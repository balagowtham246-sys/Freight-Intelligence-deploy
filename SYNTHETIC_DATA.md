# Synthetic Data Disclosure

This file is the complete, authoritative record of every place this platform
uses data that is **not** genuinely sourced from a real, citable feed.

## Why this file exists

The project brief calls for real data wherever it can be obtained, with
synthetic data used only as a last resort and disclosed in full. This file is
that disclosure. It is not documentation written after the fact: it is
**load-bearing**.

## How it is enforced

`backend/app/ingest/base.py` refuses to write any row flagged
`is_synthetic=True` unless this file contains a matching declaration line of
the exact form:

```
`source_name: some_identifier`
```

A missing entry raises `DisclosureError` and the ingestion run fails. The
check is exercised by `backend/tests/test_synthetic_disclosure.py`, which
scans the whole adapter registry, so the disclosure cannot silently drift out
of date as adapters are added.

Every row in the database also carries `source_name`, `source_url`,
`retrieved_at` and `is_synthetic`. The API returns these fields and the UI
renders a provenance badge from them, so a reader of any figure on any screen
can see where it came from without consulting this file.

## Three kinds of number, not two

Adding a forecasting layer introduced a category this file did not previously
have to name. There are now three kinds of number on the screens, and they are
badged differently:

| Badge | Meaning | Carries `ProvenanceMixin`? |
|---|---|---|
| **real** | Fetched from a named publisher and archived as fetched | Yes, `is_synthetic=False` |
| **synthetic** | Generated by us, declared below | Yes, `is_synthetic=True` |
| **modelled** | Computed by a model from data of either kind | **No** — see below |

**Model output is not synthetic data, and it does not use `ProvenanceMixin`.**
A forecast is a claim about the future derived from inputs, not a fabricated
observation of the past, and conflating the two would make both labels
useless. Forecasts, backtest metrics and alerts therefore live in tables
(`forecast_runs`, `forecast_points`, `backtest_metrics`, `alerts`) that carry
`model_name`, `model_version`, `trained_through` and the list of input series
instead of a source URL and a synthetic flag.

The consequence that matters: `/api/meta/provenance-summary` and the "% real"
badge in the sidebar count *ingested observations only*. A forecast can never
inflate or dilute that number.

The second consequence: a forecast trained on a synthetic series inherits that
taint and must say so. `ForecastRun.input_series` records exactly which series
a model was fitted on, the API returns it, and the UI shows a synthetic badge
on any forecast whose inputs include a `SYN_` series.

## Current status

**As of 2026-09-03, this platform contains one active synthetic source:
`synthetic_freight_history`.** Everything else is real.

Real data held, fetched live from its publisher and archived to
`backend/data/raw/` in its original form:

| Data | Source | Volume held |
|---|---|---|
| Paradip daily traffic (working / waiting / expected vessels) | Paradip Port Authority daily traffic PDFs | 73 daily reports, 4,445 vessel records, 2026-06-18 to 2026-09-01 |
| Monthly commodity prices (coal, crude, iron ore, gas) | World Bank Pink Sheet | 6 series, 4,392 observations, from 1960 |
| CEA plant coal stock and days-of-burn | CEA daily coal report | 191 plants |
| CDFI route-level freight assessments | Shanghai Shipping Exchange | 10 series, capturing forward daily |
| North Indian Ocean cyclone best tracks | IBTrACS (NOAA), IMD RSMC New Delhi columns | 30 seasons |
| East Coast India port and berth constraints | Port authority and terminal operator published limits | 8 ports, 24 berths |
| Vessel class particulars | Standard naval architecture references | 8 classes |

The vessel class particulars deserve a word, because they sit at the edge of
this definition. They are **representative archetypes** of each class, not
measurements of a specific named ship: a "Supramax" here is a typical modern
58,000 DWT vessel. They are not synthetic in the sense of being fabricated to
fill a gap. They are how the industry itself reasons about vessel classes,
and the engine accepts a real named vessel's particulars in place of the
archetype wherever those are known. Derived quantities such as TPC are
computed from documented naval architecture relations, and those derivations
are stated in `backend/data/reference/vessel_classes.yaml`.

## Active synthetic sources

### 1. Freight route history — `synthetic_freight_history`

- **What:** daily history for the five CDFI coal routes, written under
  `SYN_`-prefixed series codes, eight years deep.
- **Why not real:** the Shanghai Shipping Exchange history endpoint
  (`/singleIndex/cdfi`) is subscriber-gated and returns HTTP 500 without a
  session. The free `currentIndex` endpoint returns only the current
  assessment and the previous publication date. On the day the adapter is
  switched on, the platform holds two real observations, which will not train,
  calibrate or backtest anything.
- **Method:** implemented in `backend/app/ingest/synthetic_history.py`, and
  the module docstring is the authoritative description. In summary:

  - **The level is real.** Each path is rescaled so its final value equals the
    real CDFI assessment observed today. We do not invent a level.
  - **The cycle is real.** The systematic component is a regression on the
    real World Bank monthly Australian thermal coal price already held in this
    database (`COAL_AU_NEWC`, back to 1970), interpolated to daily.
  - **The stochastics are assumed.** An AR(1) idiosyncratic component with
    `phi = 0.97` (near-unit-root, because dry bulk freight genuinely is),
    GARCH(1,1)-shaped innovations so volatility clusters, annualised
    volatility of 55%, and a Fourier annual seasonal term of 8% amplitude
    peaking into northern hemisphere restocking.
  - Seeded per series code, so the disclosed dataset is reproducible.

- **Separation from real data:** synthetic history is written under distinct
  `SYN_` series codes and is never mixed into the real CDFI series. The real
  series accumulates alongside from day one and takes over as the training set
  the moment it is deep enough, with no migration.
- **Restriction:** this series may be used as a training and development
  target. It may **never** be used as a benchmark, for the reason given in
  entry 2 below. `backend/app/ml/evaluate.py` enforces this in code.
- **Status:** active.

## Anticipated entries

The items below are expected to require synthetic data, because the real
source is behind a paid licence or does not exist in any public form. **None
of these are active yet.** Each will be filled in with its generation method
and a declaration line at the moment it is first written, and not before.

### 2. FFA forward curves

- **What:** forward freight agreement settlement curves by class and quarter.
- **Why not real:** exchange-licensed data (SGX, EEX, Baltic).
- **Note:** this one carries a specific honesty risk. The strategy document
  correctly identifies the FFA curve as *the benchmark the forecast must be
  measured against*. A synthetic FFA curve **cannot** serve as that benchmark,
  because beating a curve we generated ourselves proves nothing. Where the
  FFA curve is used as a benchmark rather than as a feature, the platform will
  report "benchmark unavailable" rather than a fabricated comparison.
- **Status:** not implemented, and deliberately so. The forecaster is
  benchmarked against a random walk and a seasonal naive baseline, both of
  which are computed from the target series itself and are therefore honest
  regardless of whether that series is real or synthetic.

### 3. Internal fixture history

- **What:** a chartering desk's own record of past fixtures, used for the
  economic backtest and the "versus what the desk actually paid" comparison.
- **Why not real:** this is a real company's confidential commercial record.
  We are not that company and no such dataset exists for us to use.
- **Planned method:** generate a fixture book consistent with real published
  index levels and real port constraints, clearly flagged.
- **Status:** not yet implemented.

### 4. Demurrage, despatch and laytime terms

- **What:** per-berth demurrage and despatch rates and laytime conventions.
- **Why not real:** commercially confidential, negotiated per charterparty.
- **Current handling:** the timing engine takes demurrage rate as an explicit
  caller-supplied input with a documented default, in the same way the
  loadable-tonnes engine takes tide height. The default is stated at the call
  site and surfaced in the API response, so no confidential figure is implied
  to be authoritative.
- **Status:** not synthetic; explicit input with a disclosed default.

### 5. Berth discharge rates

- **What:** achieved discharge rate per berth per cargo type.
- **Why partially real:** some ports publish rated capacity; many do not.
- **Planned method:** published figures where available; otherwise derived
  from published annual throughput divided by observed berth-days, which is
  an estimate from real data rather than a fabrication. Estimated entries
  will be marked distinctly from published ones.
- **Status:** the current values in `port_constraints.yaml` are indicative
  and must be revisited before any cost figure derived from them is
  presented as authoritative.

### 6. Tidal predictions

- **What:** height of tide by time for the seven East Coast India ports.
- **Why not straightforwardly real:** INCOIS publishes no open API.
- **Real path, to be attempted first:** `pyTMD` evaluated against a global
  tide model (FES2014 / TPXO) at each port position. This is real harmonic
  prediction from a published model and would **not** be synthetic.
- **Fallback if model access is not obtained:** harmonic reconstruction from
  published mean spring tidal range and establishment, which *would* be
  synthetic and would be declared here.
- **Status:** not yet implemented. The engine currently accepts tide height
  as an explicit caller-supplied input and defaults to zero, so no tidal
  figure is invented anywhere.

### 7. Pre-capture AIS history

- **What:** vessel positions before live capture began.
- **Why not real:** the free AISStream feed is live-only with no historical
  backfill.
- **Planned method:** none. Congestion history before capture starts is
  derived from the archived port berthing PDFs, which are real. Any residual
  gap is left as a gap and reported as such rather than filled in.
- **Status:** not applicable; no synthetic AIS will be generated.

### 8. Bunker prices

- **What:** daily VLSFO and MGO at Singapore, Fujairah and Rotterdam.
- **Why not real:** Ship & Bunker publishes free daily prices, but the page
  renders its tables in JavaScript with no underlying JSON endpoint, so it
  cannot be parsed without driving a browser.
- **Current handling:** not synthesised. The timing engine takes bunker price
  as an explicit caller-supplied input with a documented default, and the
  response states the figure used. Real Brent (`CRUDE_BRENT`, back to 1960)
  is already held and is used as the cost-side market feature.
- **Status:** not synthetic; explicit input with a disclosed default.
